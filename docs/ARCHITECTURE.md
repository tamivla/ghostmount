# Архитектура проекта ghostmount

> Техническая спецификация компонентов, потоков данных, интерфейсов и модели безопасности.

---

## 1. Обзор

ghostmount — модульная система, обеспечивающая монтирование зашифрованных томов хранения для Nextcloud по требованию. Состоит из четырёх логических слоёв:

1. Клиентский слой: Мобильное приложение (Android) или CLI, отправляющие аутентифицированные команды.
2. Слой шлюза: SSH-демон с ограниченной обёрткой команд, которая валидирует и маршрутизирует запросы.
3. Ядро: Движок протокола, интерпретирующий команды, управляющий состоянием и применяющий политики безопасности.
4. Слой адаптеров: Подключаемые драйверы для конкретных бэкендов хранилищ (файл LUKS, раздел диска, rclone, iSCSI и др.).

Поток данных: Клиент → SSH → Шлюз → Ядро → Адаптер → Блочное устройство → Точка монтирования → Nextcloud External Storage.

Все компоненты спроектированы для эфемерной работы: тома отмонтированы по умолчанию, ключи никогда не сохраняются на диске, логи аудита структурированы и опциональны.

## 2. Компоненты

### 2.1 Клиент (мобильное приложение/CLI)

- Отвечает за: аутентификацию пользователя (биометрия/PIN), построение команд, управление SSH-сессией, отображение статуса.
- НЕ хранит: пароли LUKS, пути на сервере, бизнес-логику.
- Связь через: SSH с ключом Ed25519, сессии с одной командой, JSON-полезная нагрузка в SSH_ORIGINAL_COMMAND.
- Вывод: человекочитаемый статус, коды ошибок, опциональный локальный аудит-лог (зашифрованный).

### 2.2 Шлюз (sshd + обёртка)

- Точка входа на сервере. Настраивается через authorized_keys с ограничением command=.
- Валидирует: HMAC-подпись, свежесть nonce, роль пользователя (если многопользовательский режим).
- Передаёт: валидированную команду в Ядро через stdin или Unix-сокет.
- Логирует: минимальные метаданные (временная метка, пользователь, тип команды) в структурированный лог; никогда не логирует ключи или пути.

### 2.3 Ядро (движок протокола)

- Парсит JSON команды: {"action":"mount","vault_id":"abc","nonce":"xyz","hmac":"..."}.
- Применяет: идемпотентность (повторный mount = холостой ход), политики таймаутов, режим паники.
- Управляет состоянием: реестр активных томов в памяти, очистка при завершении.
- Генерирует события: vault.opened, vault.closed, auth.failed в вебхук или локальный лог.

### 2.4 Адаптер (драйвер бэкенда хранилища)

- Интерфейс: open(params) -> bool, close(params) -> bool, status(params) -> dict.
- Реализации: 
  - luks_file: локальный LUKS-контейнер через losetup + cryptsetup.
  - luks_block: физический раздел диска через cryptsetup.
  - veracrypt: контейнер VeraCrypt через CLI veracrypt (опциональная зависимость).
  - rclone_remote: удалённый файл через rclone mount + LUKS (доступен режим копирования в tmpfs).
  - iscsi_target: сетевое блочное устройство через iscsiadm + cryptsetup.
- Каждый адаптер обрабатывает: подготовку устройства, восстановление при ошибках, очистку при сбое.

### 2.5 Интеграция (хук Nextcloud)

- Срабатывает при событиях монтирования/размонтирования.
- Действия: occ files:cleanup, occ files:scan --path=/mnt/vault, вебхук в приложение Nextcloud (опционально).
- Гарантирует: индекс Nextcloud отражает актуальное состояние ФС; отсутствие устаревшего кэша после размонтирования.

## 3. Спецификация протокола

### 3.1 Формат команды (JSON через SSH_ORIGINAL_COMMAND)

```json
{
  "version": "1.0",
  "action": "mount|unmount|status|panic",
  "vault_id": "уникальный-идентификатор",
  "user_id": "опционально-пользователь-для-многопользовательского-режима",
  "nonce": "случайная-строка-временная-метка",
  "hmac": "sha256(action+vault_id+nonce+timestamp, key=общий-секрет)"
}
```

### 3.2 Формат ответа (stdout, JSON)

```json
{
  "status": "ok|error",
  "code": "OK|ERR_AUTH|ERR_VAULT|ERR_NETWORK|ERR_TIMEOUT",
  "message": "Человекочитаемое описание",
  "data": { "mounted": true, "path": "/mnt/vault", "active_since": 1234567890 }
}
```

### 3.3 Свойства безопасности

- Аутентификация: HMAC-SHA256 с предварительно общим ключом (хранится в Android Keystore / конфигурации сервера).
- Защита от повторов: nonce должен быть уникален в пределах 5-минутного окна; сервер отслеживает недавние nonce.
- Целостность: вся полезная нагрузка покрыта HMAC; любое изменение делает подпись недействительной.
- Конфиденциальность: SSH-туннель обеспечивает шифрование при передаче; ключи никогда не передаются в открытом виде.
- Авторизация: опциональное поле user_id для ролевого контроля доступа (RBAC) в многопользовательском режиме.

### 3.4 Обработка ошибок

- Сбой сети: клиент повторяет попытку с экспоненциальной задержкой (макс. 3 попытки).
- Некорректный HMAC: сервер возвращает ERR_AUTH, увеличивает счётчик сбоев, опционально генерирует алерт.
- Сейф не найден: ERR_VAULT с сообщением "vault_id неизвестен".
- Таймаут во время операции: адаптер откатывает частичные изменения, возвращает ERR_TIMEOUT.

## 4. Модель безопасности

### 4.1 Предположения об угрозах

- ОС сервера может быть скомпрометирована (атакующий получил root).
- Веб-интерфейс Nextcloud может быть эксплуатирован (RCE, SQLi, уязвимость плагина).
- Мобильное устройство может быть утеряно или украдено (но не рутировано в базовой модели).
- Сетевой канал защищён SSH; MITM предотвращается фиксацией ключа.
- Физический доступ к серверу контролируется (дата-центр с журналами доступа).

### 4.2 Меры защиты

| Угроза                            | Мера смягчения                                                                                                 |
|-----------------------------------|----------------------------------------------------------------------------------------------------------------|
| Атакующий получил root на сервере | Том LUKS отмонтирован по умолчанию; ключ никогда не на диске; монтирование требует аутентифицированной команды |
| RCE в Nextcloud                   | Файлы недоступны, когда том отмонтирован; путь External Storage указывает на пустую директорию                 |
| Кража мобильного устройства       | Блокировка по биометрии + Android Keystore; SSH-ключ неэкспортируемый; удалённая отзыв через ротацию ключа     |
| Атака повтором                    | Валидация nonce + 5-минутное окно + кэш nonce на сервере                                                       |
| Форензика-анализ                  | Отсутствие постоянных скриптов; логи ротируются/фильтруются; ключ стирается из памяти после использования      |
| Внутренняя угроза (админ)         | Логи аудита отправляются во внешний SIEM; режим паники мгновенно закрывает все сейфы                           |

### 4.3 Управление ключами

- Ключ LUKS: никогда не хранится на сервере; передаётся через stdin при cryptsetup luksOpen --key-file=-.
- HMAC-ключ: хранится в Android Keystore (клиент) и конфигурационном файле сервера с правами 0600.
- Ротация: поддержка ротации ключей через команду action:"rotate_key" (расширение в будущем).

### 4.4 Заметки по соответствию

- Для ПДн (152-ФЗ): обеспечить хранение логов аудита согласно политике; запросы доступа аутентифицированы.
- Локализация данных: слой адаптеров может применять ограничения по местоположению (например, отказ в монтировании, если бэкенд вне юрисдикции).

## 5. Сценарии развёртывания

### 5.1 Личный VPS (базовый)

- Nextcloud + ghostmount на одном VPS.
- LUKS-контейнер: /var/lib/ghostmount/vault.img.
- Точка монтирования: /mnt/ghostmount_vault (владелец www-data).
- SSH-пользователь: ghostmount с ограниченной оболочкой и обёрткой команд в authorized_keys.
- Авто-размонтирование: таймер systemd или сторож неактивности (по умолчанию 5 минут).

### 5.2 Гибридный: VPS + домашний NAS

- Nextcloud на VPS; LUKS-контейнер на домашнем NAS (rclone WebDAV/SFTP).
- При монтировании: копирование контейнера в /tmp/vault.img (tmpfs, ограничен по размеру), открытие LUKS, монтирование.
- При размонтировании: синхронизация изменений обратно на NAS, стирание копии из tmpfs, закрытие LUKS.
- Требует: стабильный канал, rclone с --vfs-cache-mode full, размер tmpfs >= размер контейнера.

### 5.3 Корпоративный: Многопользовательский, RBAC

- Центральный сервер ghostmount; несколько экземпляров Nextcloud или пользовательских директорий.
- Адаптер поддерживает маппинг user_id: сейф A → пользователь Alice, сейф B → группа Finance.
- Логи аудита передаются в SIEM через вебхук; режим паники доступен только роли безопасности.
- Интеграция с LDAP/AD для валидации пользователей (опционально).

### 5.4 Изолированный: Физическое разделение

- Диск LUKS физически отключён; монтируется только через локальную консоль или аппаратный KVM.
- Мобильное приложение отправляет команду через Bluetooth-последовательный мост или оффлайн QR-код (в будущем).
- Отсутствие сетевой зависимости для критического пути; SSH используется только для удобства.

## 6. Точки расширения

- Новый адаптер: Реализовать интерфейс IStorageAdapter; зарегистрировать в core/adapters/registry.py.
- Кастомная аутентификация: Заменить HMAC на JWT, OAuth2 или FIDO2, реализовав IAuthenticator.
- Плагины вебхуков: Подписка на события ядра (vault.opened) для запуска внешних действий.
- Движок политик: Подключение OPA/Rego для динамических правил доступа (в будущем).
- Мобильный SDK: Публикация спецификации протокола для сторонних клиентов (CLI, десктоп, IoT).
- Все расширения должны соответствовать лицензии GPL-3.0 и принципам безопасности по умолчанию.
