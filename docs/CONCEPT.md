# Концепция проекта ghostmount

> Зашифрованное хранилище по требованию для Nextcloud. Монтируется по нажатию, исчезает по замыслу.

---

## 1. Видение

ghostmount закрывает специфический пробел в безопасности самодостаточных облаков: как хранить высококонфиденциальные данные зашифрованными на диске, в отмонтированном состоянии по умолчанию, и делать их доступными только через явные, аутентифицированные, аудируемые триггеры — при этом сохраняя полный функционал Nextcloud, когда том активен.

Это не замена клиентскому E2EE. Это серверный, zero-trust слой хранения для администраторов, которым нужно:
- Чтобы данные были физически недоступны, когда не используются
- Полный функционал Nextcloud (превью, поиск, антивирус, Collabora) в момент монтирования
- Гранулярное управление окнами доступа с мобильного устройства
- Минимальное количество следов в форензике на сервере

---

## 2. Постановка проблемы

Существующие решения вынуждают выбирать компромисс:
- Nextcloud E2EE: zero-knowledge, но ломает превью, поиск, серверную обработку, требует официальных клиентов.
- Server-Side Encryption: прозрачно, но ключи на сервере — админ/root может получить доступ к данным в любой момент.
- External Storage + ручные скрипты: гибко, но нет единого протокола, аудита, мобильного управления, высок операционный риск.

Отсутствует готовое решение, которое объединяет:
- Шифрование на уровне блока (LUKS/VeraCrypt) с монтированием по требованию
- Управление доступом с мобильного устройства, аутентифицированное и аудируемое
- Полную совместимость с Nextcloud в активном состоянии
- Скрытный режим работы: минимум логов, отсутствие постоянных скриптов, эфемерное исполнение
- Единый интерфейс для разных бэкендов хранилищ (локальный диск, удалённый файл, сетевой блок)

## 4. Сценарии использования

#### UC-1: Личный защищённый сейф
- Пользователь хранит зашифрованный LUKS-файл на VPS.
- Через Android-приложение (разблокировка по биометрии) отправляет команду `mount` по SSH.
- Сервер валидирует HMAC, открывает LUKS ключом из stdin, монтирует в `/mnt/vault`.
- Nextcloud External Storage (Local) мгновенно показывает файлы.
- Через 5 минут неактивности срабатывает авто-размонтирование: том закрывается, ключ стирается.
- Пользователь может вручную выполнить `unmount` в любой момент.

#### UC-2: Корпоративное управление несколькими сейфами
- Админ безопасности имеет мобильное приложение с ролью `admin`.
- Видит список пользователей/групп и назначенные им сейфы.
- Может монтировать/размонтировать сейф для конкретного пользователя или группы.
- Все действия логируются в SIEM через вебхук.
- Тревожная кнопка: закрывает все сейфы, отправляет алерт, переходит в тихий режим.

#### UC-3: Гибридный бэкенд хранилища
- Сейф хранится на домашнем NAS через rclone mount.
- Сервер копирует контейнер в tmpfs по запросу на монтирование (настраивается).
- Работает с Nextcloud как локальный путь.
- При размонтировании синхронизирует изменения обратно, стирает копию из tmpfs.

## 5. Что проект НЕ делает

- ❌ НЕ заменяет клиентское E2EE для zero-knowledge шеринга.
- ❌ НЕ обеспечивает совместную работу с зашифрованными данными без монтирования.
- ❌ НЕ скрывает факт существования тома (только его содержимое и паттерны доступа).
- ❌ НЕ защищает от физического извлечения оперативной памяти во время активной сессии.
- ❌ НЕ выполняет автоматическую миграцию данных между бэкендами.
- ❌ НЕ включает встроенный веб-интерфейс для управления (только мобильное приложение + CLI, по замыслу).

## 6. Критерии успеха

| Метрика | Целевое значение | Способ измерения |
|---------|------------------|------------------|
| Время монтирования (холодный старт) | < 15 секунд для локального LUKS-файла | Бенчмарк-скрипт |
| Время размонтирования + стирания | < 5 секунд | Бенчмарк-скрипт |
| Следы в форензике | Отсутствие постоянных скриптов, логи ротируются/фильтруются | Аудит-чеклист |
| Совместимость с Nextcloud | 100% функций Local External Storage работают при монтировании | Интеграционные тесты |
| Надёжность мобильного приложения | 99.9% доставки команд при нестабильной сети | Нагрузочное тестирование |
| Безопасность | Отсутствие critical/high CVE в зависимостях, нет хардкод-секретов | Dependabot + ручной аудит |

## 7. Руководящие принципы

1. **Безопасность по умолчанию**: В случае сомнений — выбирать более безопасный вариант. Валидировать все входные данные. Минимизировать поверхность атаки.
2. **Эфемерность по замыслу**: Данные доступны только в явно заданные временные окна. Никаких постоянных монтирований.
3. **Минимум следов**: Отсутствие постоянных скриптов на диске, где это возможно. Логи структурированы, ротируются, опциональны.
4. **Протокол важнее реализации**: Сначала определить стабильный протокол команд; адаптеры могут эволюционировать.
5. **CLI-первым, API-вторым**: Интерфейс, удобный для автоматизации; мобильное приложение — клиент, а не источник истины.
6. **Прозрачность GPL-3.0**: Все производные работы должны оставаться открытыми. Никаких проприетарных форков ядра.
